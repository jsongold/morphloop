# contracts/openapi/

The HTTP API contract between the harness (`harness/api/`) and any UI: the
standard web UI or a custom one (ADR-0015). `v0.1.yaml` is OpenAPI 3.1, so its
schemas are JSON Schema 2020-12. No code is generated from it (ADR-0017). The
FastAPI backend and the hand-written web client are both checked against it by
contract tests.

Scope is the v0.1 learner chain only (ADR-0012). The document has no
domain-specific paths or fields.

## Endpoints

| Method and path | Purpose |
|---|---|
| `GET /health` | liveness and DB connectivity (Slice 0, unchanged) |
| `GET /packs` | imported pack versions (`pack_id`, `pack_version`, `pack_content_hash`) |
| `POST /learners` | create a learner identity |
| `GET /learners/{learner_id}/sessions` | find a session to resume |
| `GET /learners/{learner_id}/skills` | learner-skill projection |
| `POST /sessions` | start a session on one pack version (`session.started`) |
| `GET /sessions/{session_id}` | resume state: session, active attempt, UI state, `last_position` |
| `GET /sessions/{session_id}/layout` | the pack's layout document, opaque |
| `GET /sessions/{session_id}/activities` | whitelist views of the startable activities |
| `GET /sessions/{session_id}/content` | list of learner-facing documents (skill, visualization, reference) |
| `GET /sessions/{session_id}/content/{kind}/{definition_id}` | one learner-facing document |
| `POST /sessions/{session_id}/attempts` | start an attempt; the server starts the lab |
| `GET /attempts/{attempt_id}` | attempt status, current lab, evaluation result |
| `POST /attempts/{attempt_id}/submit` | submit; evaluation runs asynchronously (`202`) |
| `GET /labs/{lab_instance_id}` | lab state |
| `POST /labs/{lab_instance_id}/reset` | reset to the fixture; returns the replacement lab (`202`) |
| `WS /labs/{lab_instance_id}/terminal` | terminal and push channel, in `x-websockets` |
| `POST /sessions/{session_id}/events` | append a client-originated learner event |
| `POST /sessions/{session_id}/chat/messages` | send a chat message; the tutor reply comes back in the response |
| `GET /sessions/{session_id}/chat` | chat events; `?thread_id=` loads one thread (popup chat) |
| `GET /sessions/{session_id}/memos` | memo projection (`memo.recorded` + `memo.edited`), one per highlight thread |
| `GET /sessions/{session_id}/highlights` | highlight events |
| `GET /sessions/{session_id}/timeline` | stored events by `position`, keyset-paginated |

## Decisions

### Reuse schemas by `$id`

Request and response bodies `$ref` existing schemas by their absolute `$id`
(`contracts/README.md`), with a JSON pointer fragment where only part of a
schema is needed (for example `lab.status.json#/properties/status` or
`assistant.message_requested/1.json#/properties/references`). Only HTTP-only
shapes are defined in `components.schemas`. Stored events are always
`events/envelope/stored.json`. Where a response holds one event type, the
component narrows it with `allOf` plus an `event_type` `const`
(`HighlightEvent`, `MessageGeneratedEvent`, and so on), so payloads are never
copied.

Tools that follow `$ref`s must map `https://morphloop.dev/contracts/` to this
directory tree. The ids are names, not URLs to fetch. The contract test does
this with a local handler.

### Client events: a generic endpoint for pure facts, specific endpoints for commands

`POST /sessions/{session_id}/events` takes `content.highlighted`,
`content.opened` and `visualization.step_selected`. These are learner UI
actions whose only effect is the event and its projection. The request body
(`ClientEventRequest`) is the producer part of an append request. It `allOf`s
`events/dispatch.json`, so the payload is validated by the event payload
schema itself. A new client event type needs only a dispatch branch and one
more value in the `event_type` enum. The server fills in the fields the client
must not be trusted with: `event_id`, `learner_id`, `session_id`,
`actor: learner`, `activity_definition_id` (derived from `attempt_id`),
`causation_id` and `correlation_id`. It then validates the whole event against
`append.json`. Ids that live inside a payload, such as `highlight_id`, are
generated by the client (opaque, `hl_` prefix). A reused id is a
`409 state-conflict`.

Start, submit, reset and chat have their own endpoints. They carry side effects
(a lab, an evaluation, an LLM call), their events are partly built by the
server (`message_id`, `lab_instance_id`, provenance), and their responses are
not a single stored event. Putting them behind the generic endpoint would hide
the side effects behind an event type string.

### Tutor reply: synchronous in the HTTP response

`POST .../chat/messages` appends `assistant.message_requested`, calls the
tutor, appends `assistant.message_generated` and returns both stored events
(`ChatExchange`). Reasons:

- The WebSocket is scoped to a lab instance. Chat also happens outside an
  attempt or while a lab is resetting, when no socket exists.
- `event.appended` is deliberately thin (`ws/README.md`), so a push would still
  need a follow-up fetch.
- One tutor call is short enough for a request/response in v0.1. Streaming can
  be added later as a new endpoint or WS message without changing this one.

If the tutor call fails or its output fails validation, the request event stays
recorded and the response is `502 llm-failed`. Resending the same
`idempotency_key` appends no second request event and retries the reply.

### Evaluation: asynchronous (`202`), polled or pushed

Submit runs checks, the LLM evaluator and the LLM learner model, which is
several calls. `POST /attempts/{attempt_id}/submit` returns `202` with the
attempt in `evaluating`. The client polls `GET /attempts/{attempt_id}` or
refetches when `event.appended` announces `activity.completed` on the lab
socket, which is open during an attempt. The result is the stored chain
`evaluation.completed` → `evidence.created` → `learner_skill.updated` →
`activity.completed` (AC-A3, AC-F3). An LLM output that fails validation
changes no state (AC-E4). The attempt returns to `active` with
`last_submission_error` set.

### Labs are server-driven

The client never starts or destroys a lab. Starting an attempt starts its lab.
Reset is the only learner lab command, and it targets a specific instance
(`/labs/{lab_instance_id}/reset`). Resetting an instance that was already
replaced is therefore a detectable conflict, not a second reset. A reset
creates a new LabInstance in the same attempt (ADR-0007). The old socket
closes and the client connects to the new instance's `terminal_path`.

### Idempotency (ADR-0008, AC-F5)

- Every `POST` that appends events requires `idempotency_key` in the body. The
  key becomes the `idempotency_key` of the primary event (`session.started`,
  `activity.started`, `activity.submitted`, `lab.reset`,
  `assistant.message_requested`, or the client event). The server derives keys
  for the follow-on events it appends.
- The key is in the body, not an `Idempotency-Key` header, so the generic
  events endpoint and the command endpoints use one mechanism, and the key is
  the same value that ends up on the event.
- Same key and same body: nothing is appended, and the original status and body
  are returned with `Idempotent-Replayed: true`. For `202` commands this is the
  original body, not the current state.
- Same key and a different body: `409 idempotency-key-reused`.
- Keys are unique across the store (`ids.json`). Clients should namespace them,
  for example `web:<ULID>`.
- `POST /learners` appends no event and takes no key.

### Highlight threads and memos

A highlight `hl_<tail>` owns the popup thread `thr_<tail>` and the memo
`memo_<tail>`. The ids are derived, so no binding event exists and the popup
can load an empty thread before the first message. The popup reuses
`POST .../chat/messages` (with that `thread_id`) and `GET .../chat?thread_id=`.
After each tutor reply in a highlight thread the server runs the pack's memo
summarizer and appends `memo.recorded`, unless the learner already edited that
memo. The memo comes back in `ChatExchange.memo`. A learner edit is a pure fact
and goes through the generic events endpoint as `memo.edited`. Memos have an
edit event, so `GET .../memos` returns a view (`MemoView`), not events.

### Timeline pagination

Keyset pagination on `position`: `after_position` (exclusive) and `limit`
(default 100, maximum 500). The response returns `last_position` and
`has_more`. `session.last_position` from `GET /sessions/{id}` tells a resuming
client where the log ends. The timeline includes `terminal.output` chunks
(AC-B3). The contract guarantees that paging forward never skips an event.
ADR-0008 notes that the order in which positions are assigned can differ from
the order in which transactions commit. A timeline reader tracks `position`, so
the server must serialize appends per session or hold back pages at an
uncommitted gap.

### Projections that equal their events

v0.1 has no edit or delete events for highlights or chat, so the highlight and
chat endpoints return the stored events themselves instead of a second shape.
When such events are added, these endpoints get a view schema. `UiState` (open
side-pane content and the selected step per visualization) reuses the
`content.opened` and `visualization.step_selected` payload schemas.

### Learner-facing pack views (AC-J6)

`contracts/schemas/pack/` was being written at the same time, so this document
does not reference it. What reaches the learner is decided by a whitelist:

- `ActivityView` has only `title`, `activity_type`, `skill_ids`, `lab_backed`
  and the verbatim `instructions` object, plus the id and hash. Hints are left
  out because v0.1 has no hint-request event. Hints reach the learner through
  the tutor in hint mode.
- `ContentKind` is `skill | visualization | reference`. Every other kind
  (reference solution, environment, template, generation record, evaluator)
  has no route.
- `ContentDocument.document` and the layout are served as opaque objects. When
  the pack schemas are frozen, `document` can `$ref` them per kind.

### Errors

One shape: RFC 9457 problem details (`application/problem+json`) with a closed
`code` enum: `invalid-request` 400, `not-found` 404, `idempotency-key-reused`
409, `state-conflict` 409, `validation-failed` 422 (with `errors[].path`),
`llm-failed` 502, `lab-unavailable` 503, `internal` 500.

### WebSocket

OpenAPI cannot describe WebSockets. The root `x-websockets` extension documents
`/labs/{lab_instance_id}/terminal`. It references `ws/envelope/message.json`
and `ws/dispatch.json` and lists the message direction. The messages are
defined only in `contracts/schemas/ws/`.

### No authentication in v0.1

v0.1 has a single local learner. `security` is empty and `learner_id` is
passed explicitly. Authentication is a later, additive change.

## Tests

`tests/contracts/test_openapi_contract.py` checks that:

- the document is valid OpenAPI 3.1 (`openapi-spec-validator`, a dev
  dependency);
- every external `$ref` resolves to an existing `$id` and fragment under
  `contracts/schemas/`, and none points at `schemas/pack/`;
- every internal `$ref` resolves;
- structural rules hold: event-appending `POST`s require `idempotency_key`,
  errors use `Problem`, and paths are domain-agnostic;
- example bodies validate. The stored-event examples reuse
  `tests/contracts/fixtures/events/valid/`.
